Group swap — “which album does this sticker come from / go to?”

Four ways to surface per-album routing in a combined swap. All four use the same underlying data that computeGroupPool / routeReceived / routeGiven already return — the difference is purely presentational. Colours and chip styling are the app's real tokens.

The scenario every mockup renders

  • Group “Kids' World Cup” — members Leo (green) and Kai (blue), plus Grandpa as a view-only read-only share.
  • You give: MEX-9 ×1 (Leo has the spare) · BRA-4 ×1 (Kai has the spare).
  • You get: MEX-7 ×2 (both boys missing it → one each) · MEX-3 ×1 (both missing, only one copy → ambiguous, you choose) · CC-5 ×1 (Leo tracks CC, Kai doesn't) · ARG-2 ×1 (only Grandpa needs it → hand-off, never written).
  • Each variant also gets a 4-album stress test, since groups may run to four members.

My recommendation — A for the chip screens, C for the close screen

They're not competing; they solve different jobs. A (chip badges) is the only option that leaves the existing chip grid — and its per-page grouping (MEX 🇲🇽, BRA 🇧🇷) — completely intact. On the New-swap and Detail screens the chip grid is the artifact you're scanning, and routing there is preview-only, so a passive mark is exactly the right weight.

C (flow rows) earns its vertical space only on the close screen, where every copy is a decision that's about to commit, the override control needs somewhere to live, and “one row per physical copy” matches what you're literally doing with your hands. It's also the shape the code already emits — this is .close-routes grown up, not a rewrite.

B (lanes) is the strongest single answer if you'd rather have one treatment everywhere, and it's the most legible of the four — but it fights the page grouping and duplicates a sticker that goes to two albums. D (matrix) is the most information-dense and the only one that shows the whole ledger at a glance; it reads more like a spreadsheet than the rest of the app, and it's the one I'd expect to age worst on a narrow phone.

  1. Both A and C need the same new primitive: a tinted .amark monogram derived from the existing monogram(name) + coverTint(id), so an album's colour is identical here, in the Library sheet and in the switcher.
  2. Colour is never the only signal — the letter carries the meaning, so this survives colour-blindness and greyscale.
  3. The give side stays non-interactive everywhere (spec §D: surplus is fungible); only ambiguous receives get a control, and only at close.
